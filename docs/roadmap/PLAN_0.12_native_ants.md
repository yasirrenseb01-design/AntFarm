# แผน: เก็บข้อมูลมดในวิวรังแบบใหม่ (C++ ถือ) — PART 0.12

เขียน 2026-11-10 หลัง v0.12.26. **ยังไม่ได้ลงมือ รอผู้ใช้ตอบ** ผู้ใช้เลือก "เก็บข้อมูลมดแบบใหม่" แทนการย้ายลูปทีละส่วน
เป้า: วิวในรังของรัง 861 ตัว (สำเนา `usercopy` slot 3) บน exe ที่กราฟิก "สูง" (วาด 600 ตัว) เร็วขึ้นชัดเจน ภาพเหมือนเดิมทุกอย่าง

## 1. ที่วัดได้ (ทำไมสองรอบแรกได้น้อย)

ต้นทุนต่อการเข้าถึงหนึ่งครั้ง (วัดบนตัว editor, `tests/_bench` ชั่วคราว):

| การเข้าถึง | ns |
|---|---|
| GDScript อ่าน `m.get("k", d)` / `m.k` / `m.has("k")` | 79 / 51 / 52 |
| GDScript เขียน `m.k = v` | 38 |
| GDScript อ่าน/เขียน PackedArray `a[i*K+F]` | 27 / 20 |

ข้อสรุปจากตัวเลข:
1. **ย้ายช่องไป PackedArray แต่ยังคิดใน GDScript ได้กำไรแค่ครึ่งเดียวต่อการเข้าถึง** (79 → 27 ns) และเสียความหมาย "ไม่มีช่องนี้" (`has`)
   — กำไรจริงมาเมื่อ**ทั้งงานของมดหนึ่งตัวรันใน C++ บน struct** เท่านั้น
2. v0.12.26 ย้ายลูปสแกนมดข้างเคียงของ look ahead ไป C++ แล้วได้แค่ 2.7 → 2.5 ms เพราะ C++ ยังต้องอ่าน Dictionary ของมดข้างเคียง
   ทีละตัว (~200 ns ต่อตัว × หลายสิบตัวในห้องแน่น) — **ข้อมูลที่มดอ่านจากตัวอื่นคือสิ่งแรกที่ต้องแพ็ก**
3. การเรียก C++ แพง (0.2–0.6 µs ต่อครั้ง): ต้องเรียกน้อยครั้ง — หนึ่งครั้งต่อมดต่อช่วงงาน หรือหนึ่งครั้งต่อเฟรม ไม่ใช่ต่อช่อง
4. bind ไม่ได้ช้าเพราะ Dictionary ของมด แต่เพราะอ่านวัตถุ worker ของการจำลอง — การแพ็กมดไม่ช่วย ต้องแก้แยก (ข้อ 6)

## 3. รูปแบบที่เสนอ: `NestAnts` (C++ ถือ, หนึ่งช่องต่อมดที่วาด)

- คลาส C++ ใหม่ `NestAnts` (RefCounted, หนึ่งตัวต่อวิวรัง) ถือ **struct-of-arrays** ยาวเท่าจำนวนมดที่วาด + ตัวขุด + ศพ/ตัวที่กำลังออกจากรังไหม
  (ทุกอย่างที่เป็น "ร่าง" ใน `near`). มดแต่ละตัวได้เลขช่อง `m.ix` ตอน `_add_mate` คืนช่องตอนถูกถอดใน bind (ช่องว่างใช้ซ้ำ; มีเลขรุ่นกันชี้ผิดตัว)
- ชนิดข้อมูล**ตรงกับที่ GDScript คิดอยู่**: เวกเตอร์/ทรานส์ฟอร์มเป็น float 32 บิต (Vector3, Transform3D ของเอนจิน), ตัวเลขเดี่ยวเป็น double
  (float ของ GDScript), จำนวนเต็ม 64 บิต; "ไม่มีช่องนี้" (`has`) เป็นบิตในชุดแฟล็กต่อมด ค่าเริ่มต้นของ `get("k", d)` เขียนเป็นค่าคงที่ในที่เดียว
- การชี้ไปมดตัวอื่น (`over_on cross_on partner ant_with`) เก็บเป็นเลขช่อง + เลขรุ่น; `is_same(a, b)` = เลขเท่ากัน
- **กลุ่ม A + B อยู่ใน C++** (กลุ่ม B ~85 ช่องไม่มีใครข้างนอกเขียน ย้ายได้สะอาด); **กลุ่ม C–E อยู่ใน Dictionary ต่อไป** (GDScript 20 ไฟล์ไม่ต้องแก้)
- **กติกา "ดึงเข้า–ส่งออก" ต่อมด** แทนการแก้ทุกจุดที่เขียน `m.xxx`:
  - ก่อนงานของมดตัวหนึ่ง C++ **ดึง** ช่องที่ GDScript เป็นเจ้าของและงานนั้นต้องใช้ (~15–20 ช่องของกลุ่ม C/D: `rest settle act carry script?
    partner face role…`) จาก Dictionary ของมัน (~35 ns ต่อช่อง)
  - หลังงาน C++ **ส่งออก** ช่องที่โค้ดข้างนอกอ่าน (~12 ช่อง: `xf vp vu vf mv over bend sep clr act fgap gait`) กลับลง Dictionary
    → duties, lifecycle, dev tools, `--view-hash` อ่านได้เหมือนเดิม ไม่ต้องรู้ว่ามี C++
  - ค่าใช้จ่าย: ~30 ช่อง × 40 ns × 600 ตัว ≈ 0.7 ms ต่อเฟรม แลกกับงาน ~15 ms ที่หายไป
  - ช่องส่วนตัวกลุ่ม B ที่ dev tools อ่าน (`gfit soil_off clr_own sgr…`): ส่งออกทั้งหมดเมื่อเปิดตัวเลือก dev (`--bodies`, `--trace-*`, `--follow-*`)
- ถังร่างข้างเคียง (`near`, คีย์ = ช่อง 3×3×3) สร้างใน C++ จากตารางเดียวกัน: ลูปที่อ่านตัวอื่นอ่านจาก struct (~5 ns ต่อตัว แทน ~200)
- แคชต่อช่องดิน (ground ring, cell fits, lift) ย้ายเป็น hash map ใน C++ ล้างเมื่อ `_soil_gen` เปลี่ยน; ตารางทางของ route เป็นขั้นหลัง

### ลำดับงานและเลขคณิตต้องเหมือนเดิม
- ลูปมดยัง**เรียงตาม `_mates` ทีละตัวจบทั้งตัว**เหมือนเดิม (มดตัวหลังเห็น `xf/over` ใหม่ของตัวก่อนในเฟรมเดียวกัน; `d0/d1` คิดครั้งเดียวต้นเฟรม) —
  ไม่ทำขนาน ไม่สลับลำดับ ไม่รวมเป็นรอบ ๆ ข้ามมด
- `randf()/randi()` เรียกผ่านตัวสุ่มของเอนจินตัวเดิม (`UtilityFunctions::randf`) ในลำดับเดิม; จุดที่สุ่มอยู่ใน GDScript คงไว้ที่ GDScript จนกว่าจะย้ายทั้งฟังก์ชัน
- เลขคณิต: บรรทัดต่อบรรทัดจาก GDScript, double ต่อ double, float ต่อ float, ปิด FMA (ทำแล้วใน `native/`), ใช้ `Vector3/Basis/Transform3D` ของ godot-cpp
  (ตรวจแล้วว่าตรงกับเอนจิน: `bend_probe` 20,000 ตัว, `gap_scan` 3,416 ตัว, `soil_hits`)
- สถานะที่ข้ามเฟรม (ตัวนับ `_mate_frame + mi`, งบต่อเฟรม `clr_budget`, `_gfit_budget`) ส่งเข้า/ออกทุกครั้ง ไม่เก็บซ้ำสองที่

### ทางสำรอง GDScript (`--no-native`)
- โค้ด GDScript เดิม**อยู่ครบและเป็นตัวอ้างอิง**ของการเทียบ: `--no-native` ใช้ Dictionary ล้วนเหมือนวันนี้ (ไม่ผ่าน `NestAnts`)
- ผล: ฟังก์ชันที่ย้ายแล้วมีสองฉบับ (GDScript + C++) ต้องแก้คู่กันทุกครั้งที่ปรับอนิเมชันในอนาคต — **ต้นทุนถาวรที่ผู้ใช้ควรรู้**
  (กันพลาดด้วยเทสต์เทียบค่าที่รันใน `tools/check.ps1` ทุกครั้ง)
- ไฟล์ที่ติดเพดาน `tools/size_allow.txt` (`nest_mates.gd` 886 บรรทัด ห้ามโต): ทางแยกไป C++ อยู่ในไฟล์ชั้นใหม่ (`nest_native.gd`) ไม่เพิ่มในไฟล์เดิม

## 6. เรื่องที่ต้องให้ผู้ใช้ตัดสิน
1. **bind (6.4 ms):** ช้าเพราะอ่านวัตถุ worker ของการจำลองทุกเฟรม แพ็กมดไม่ช่วย ทางเลือก:
   (ก) ทำ bind เฉพาะเมื่อการจำลองเดินหนึ่งก้าว (`sim.tick` เปลี่ยน) หรือมีมดที่วาดเปลี่ยนสถานะ — ต้องพิสูจน์ด้วย hash ว่าผลเท่าเดิมทุกเฟรม;
